astra-tools v0.3.0rc2

Data model¶

The data model is what the functions of astra.api return, and what a runner hands back. It is defined in src/astra/model/, a file for each thing a function returns, and those files hold nothing else.

File Classes Where they come from
validation_report.py ValidationReport validate returns it
resolved_analysis.py ResolvedAnalysis and the classes it is made of resolve returns it
status_report.py StatusReport, Status, EvidenceStatus status returns it
provenance_record.py ProvenanceRecord, Generation and its parts a runner gives write_records a Generation; a Status holds the record
diagnostic.py Diagnostic, Location the reports hold them
paper.py Paper, QuoteStatus the paper functions return them

Every class is imported from astra.api.

Conventions¶

  • Plain data. Every class is a frozen dataclass that holds what JSON holds: text, numbers, true and false, lists and maps. In Python a list is a tuple, and a map a read-only mapping.
  • A reference is an id, never an object. Where one element names another, it holds the other's id as text, and a reader looks it up.
  • Each fact once. What a reader gets by following a reference isn't repeated.
  • One JSON form. Each class writes as a JSON object that holds every field under its name. An optional field is left out where it has no value, and is never null. A list or a map is always there, empty or not. ValidationReport, ResolvedAnalysis and StatusReport have a to_json() method that gives it.

In the tables below, optional marks a field that can have no value.

JSON report contract¶

Each report carries a fixed schema_version: astra-tools.validation-report.v1, astra-tools.resolved-analysis.v1 or astra-tools.status-report.v1. This identifies the JSON format, independently of the authored ASTRA spec_version and the astra-tools package version. The field is set by the report class and adds no constructor argument.

The packaged reports.schema.json is a JSON Schema 2019-09 document. Its $defs contain the three report types and their nested types; the document itself accepts any of the three reports. Other languages can consume it without Python. It checks transport structure, not reference integrity or the rules applied by validate, resolve and status. In Python, read it with:

from importlib.resources import files

schema_json = files("astra.model").joinpath("reports.schema.json").read_text("utf-8")

Within a format version, producers may add optional fields; readers should ignore unknown fields. Removing or renaming a field, changing its type or meaning, adding a required field, or making an optional field required needs a new format version. Lists keep the ordering described below; JSON object member order is not part of the interchange contract. Optional fields remain omitted, never null.

Generate the schema from the Python model with uv run --frozen python scripts/generate-report-schema.py; tests check it for drift. Small, reproducible report fixtures provide expected JSON for independent implementations; they supplement the specification's validation conformance suite.

The diagrams are UML class diagrams. A filled diamond is on a class that holds another; a hollow diamond is on a class that refers to another by its ref or id. The number beside a class says how many, and [0..1] after a field marks an optional one, [*] a list.

The resolved analysis¶

A resolved analysis is an analysis with every rule of the specification already applied. Two rules decide what is in it.

It holds what the rules give, not what they start from. Where an astra.yaml writes something only for a rule to act on, the model holds the outcome: a universe's effective selection and no derived_from, what each entry of an output's inputs reads and no switch, a command as it runs and no template. What a file writes for people to read stays as written: labels, descriptions, rationales, claims, quotes.

It holds each fact once. A result carries its places, what it reads and its command. It carries neither the options it is made with (its output's decisions, looked up in its universe's selection) nor the folder its recipe runs in (its output's analysis's folder).

References, ids and paths¶

  • A ref names an element among all the analyses of the stack: its analysis's key, the collection the file writes it in, and its id, joined by dots. outputs.fit is an output of the driving analysis, and stage.decisions.method a decision of the analysis stage.
  • An analysis's key is its canonical address: the shortest chain of declarations that reaches it from the driving analysis, the first in alphabetical order among equals, and "" for the driving analysis itself.
  • A result's id is its address, as its record gives it (fit#baseline), after the key of the analysis it belongs to and a colon where that isn't the driving analysis (stage:fit#v1).
  • Every path is a path from the driving analysis's folder, with / between folders and . for that folder itself. A file of an analysis read at a commit is in that commit's tree, from the top of the repository it is read in. A diagnostic's location isn't such a path: it names its file from the top of the repository.

ResolvedAnalysis¶

Field Type Meaning
spec_version str The driving analysis's spec_version
head str, optional The commit the repository is on, as HEAD names it; none where it has no commit yet
analyses list of Analysis The driving analysis, then each it declares, directly or not, by key
results list of Result The results, each after every result it reads
notes list of Diagnostic What an author may want to tidy, which breaks no rule
schema_version str Always astra-tools.resolved-analysis.v1; the JSON report format

The notes are FALLBACK_PIN, UNPLANNED_OUTPUT and NOT_BUILT, at the level note, and the runner rule CODE_OUTSIDE_ANALYSIS, a warning.

head names the commit, not the files: the analysis is read in the working tree, so where a file is edited and not committed, two readings at the same head can differ. A StatusReport has the same field, so a reader that asked for both can tell that nothing was committed between the two.

Result¶

A result: one output, in one universe or once.

The results are those of the outputs the driving analysis builds, each in every universe that builds it, and the results those read, in whatever analysis they belong to. The specification says the analysis plans these. An output with no result, such as one of a declared analysis that nothing reads, is named in the notes.

Field Type Meaning
id str
output str Its output, by ref
places list of Place Where it is kept: one place, unless its analysis is driven through two chains of declarations
universe str, optional Its universe, by ref; none for an output built once
inputs list of Source One for each entry of its output's inputs, in order
command str, optional Its recipe's command as it runs, in the folder of its output's analysis, with each path relative to that folder
commit Commit, optional The commit whose tree its places are in, where the analysis it belongs to is read at one; none for a result whose places are in the working tree

A result has no command where it isn't built from the working tree alone: a result of an analysis read at a commit, one whose recipe runs on a commit's files, or one that reads a file at a commit.

A result with a commit is a result from a commit: it is never built, its record is the one at that commit, and write_records refuses it.

Field Type Meaning

record_path str Where its record goes
file_path str The result's file, where its bytes go. A stand-in may be there in their place: its Status says

Source¶

What one entry of an output's inputs reads for a result: an input, or another result, through any pin and the case each switch on the way takes. It has input or result, never both.

Field Type Meaning

input str, optional The input it reads, by ref
result str, optional The result it reads, by id

The status report¶

A status report says how the results of an analysis stand: one status for each result of the resolved analysis, with the records and bytes that are in the working tree. It holds none of the analysis itself. Each status is under its result's id, and resolve gives the result.

A result is unchanged where it has a record at each of its places and nothing it is made from has changed since the commit the record names; stale where something has; and missing where a place has no record that is the result's own.

Separately, the report says where the bytes of each result and of each input are: present where reading the file gives its content, and absent otherwise. A result's state doesn't depend on its bytes, so a clone that hasn't fetched what a large-file tool keeps reads as up to date, with those bytes absent.

Field Type Meaning

Status¶

A result's status: the worst of its places'.

Field Type Meaning
state str unchanged, stale or missing
bytes Bytes, optional Where its bytes are; none for a result of an analysis read at a commit that no recipe reads
record ProvenanceRecord, optional Its record, where every place holds one that is the result's: the first place's
why list of Diagnostic Each rule the result itself breaks
stale_inputs list of str Each entry of its output's inputs that reads a result that isn't unchanged, or one made again since with other bytes than the record gives

A result that is stale with no error in why is stale only through what it reads. It is unchanged again once each of those is built with the bytes its record gives for the entry, which a runner that builds them can tell without a second check.

Bytes¶

Whether the content of a file the analysis names is in this clone: an input's, or a result's.

Field Type Meaning
state str present where reading the file's path gives the content; absent otherwise. For a result, the content is the one its record gives
kept_by str, optional The tool whose stand-in is at the path: git-annex, Git LFS or DVC

absent with a kept_by means the content needs fetching, with that tool. astra-tools never fetches: when and how is a runner's to decide.

A stand-in is what a large-file tool keeps in a file's place. astra-tools reads three:

Tool Its stand-in The content is here when Compared without the content
git-annex, locked file A link at the path, into an annex/objects folder The link leads to a file Yes, for a key of a SHA-256 backend, which is the default
git-annex, unlocked file A pointer file at the path, only while the content isn't fetched The path holds the content Yes, the same
Git LFS A pointer file at the path, only while the content isn't fetched The path holds the content Yes
DVC A .dvc file beside the path A file is at the path, or a link from DVC's cache No: it gives an MD5, and a record a SHA-256

So with git-annex and Git LFS, an analysis whose inputs and results aren't fetched validates, and its results read unchanged. With DVC, results that aren't fetched read unchanged too, but an input kept by DVC must be pulled for the results made from it to be compared: until then they read stale. The same holds for a git-annex key of a backend other than SHA-256.

astra-tools follows a link only for a stand-in, as the operating system follows it:

  • a git-annex link, to the file it leads to, where that file really is in an annex/objects folder. So a submodule or a linked worktree works, whose object store is outside its tree, and a link merely dressed as git-annex's leads nowhere;
  • what is at the path beside a DVC file, wherever it leads, as DVC's cache can be anywhere.

A link that is no stand-in's is never followed. This favours convenience: a repository can make astra status say whether a file is at a path of your machine, and whether it has a hash the repository gives, by a link beside a .dvc file. It never shows a file's content. That matters only where you run astra on a repository you don't trust and show its output.

kept_by names the stand-in that is on disk. A file whose content a tool has put in place of its pointer, as git-annex does for an unlocked file and Git LFS always, reads as a plain file.

ABSENT_RESULT, a warning, is for bytes that are neither at a result's file nor stood in for there: no file, other bytes, or a stand-in for other bytes. A stand-in for the recorded bytes breaks no rule.

EvidenceStatus¶

An item of evidence that cites an output, and the status it gets: the worst of the results it cites, and missing where it cites none.

Field Type Meaning
insight str The insight it backs, by ref

state str unchanged, stale or missing
why list of Diagnostic STALE_EVIDENCE, where it isn't unchanged

The provenance record¶

A record is a runner's account of how it made a result, kept at the result's place. What it says is the runner's to find out, and true of its run. The classes have the fields of the specification's record schema.

classDiagram
  direction LR
  class ProvenanceRecord {
    address : str
    content_hash : str
    size : int
    spec_version : str
  }
  class Generation {
    commit : str
    started : str [0..1]
    finished : str [0..1]
  }
  class RecordedInput {
    entry : str
    content_hash : str
    size : int
  }
  class Environment {
    iri : str
  }
  class Runner {
    id : str
    version : str
  }
  ProvenanceRecord *-- "1" Generation : generated_by
  Generation *-- "1" Environment : environment
  Generation *-- "1" Runner : runner
  Generation *-- "*" RecordedInput : inputs

ProvenanceRecord¶

Field Type Meaning
address str The result's address at this place
content_hash str The hash of the result's bytes, as sha256:<hex>
size int Their size, in bytes
generated_by Generation The run that made it
spec_version str The version of the specification the record is written for

Generation¶

A run of an output's recipe.

Field Type Meaning
commit str The commit it ran from
environment Environment The environment it ran in
runner Runner The runner that ran it
inputs list of RecordedInput What it read: one for each entry the output's inputs lists
started str, optional When it started, in UTC to the millisecond: 2026-10-26T14:00:00.000Z
finished str, optional When it finished

The times are text, as the record writes them.

RecordedInput¶

What a recipe read through one entry of its output's inputs.

Field Type Meaning
entry str The entry, exactly as written
content_hash str The hash of what was read
size int Its size, in bytes

Environment¶

The environment a recipe ran in.

Field Type Meaning
iri str An IRI its runner can recreate the environment from

Runner¶

The runner that ran a recipe.

Field Type Meaning
id str The runner's name
version str Its version

Example¶

{
  "address": "fit#baseline",
  "content_hash": "sha256:2f52064dbe4ae7fa6932e26efc33bdf8c4e38b9fb958d8e34a08d51e72d0de5a",
  "generated_by": {
    "commit": "b0e28a260c752e8060197b5f788086c53233cb4f",
    "environment": {"iri": "urn:example:python-3.13"},
    "finished": "2026-11-15T10:04:22.950Z",
    "inputs": [
      {
        "content_hash": "sha256:9c6536d38fa37da58fac066342747e6d20fdace12ab5b287cf04506f2afe95b0",
        "entry": "catalog",
        "size": 4
      }
    ],
    "runner": {"id": "example-runner", "version": "0.1.0"},
    "started": "2026-11-15T10:04:22.931Z"
  },
  "size": 28,
  "spec_version": "0.1.0"
}

Papers¶

A paper is a work that evidence cites by its DOI, kept as a PDF in the paper cache.

classDiagram
  direction LR
  class Paper {
    doi : str
    version : int [0..1]
    pdf_path : str
    content_hash : str
    retrieved : str
    title : str [0..1]
    authors : str [*]
    source_url : str [0..1]
  }
  class QuoteStatus {
    state : found, elsewhere, not_found or no_paper
    page : int [0..1]
  }

Paper¶

Field Type Meaning
doi str Its DOI, as it was added
pdf_path str Its PDF, as an absolute path
content_hash str The hash of the PDF's bytes, as sha256:<hex>
retrieved str When it was put in the cache, in UTC
version int, optional The version of an arXiv paper
title str, optional
authors list of str
source_url str, optional Where the PDF was got from

QuoteStatus¶

Whether a quote is in the paper it is said to be in.

Field Type Meaning
state str found; elsewhere, in the paper but not on the page its location gives; not_found; or no_paper, where the paper isn't in the cache
page int, optional The page it is on, from 1, where it is in the paper 
{"state": "found", "page": 2}
